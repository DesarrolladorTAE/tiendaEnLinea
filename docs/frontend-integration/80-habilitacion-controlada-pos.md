# Habilitación controlada del POS

## Controles de compilación

En `vite.config.mjs:4–15`, Vite incorpora los valores al frontend. `VITE_POS_SERVICES=true` habilita la nueva operación POS, la reserva y recuperación idempotentes V2 y la administración de estado de terminales solo con `command=serve`, modo distinto de producción, `VITE_API_URL` configurada y sin opt-in a la API de producción. `VITE_POS_VEHICLE=true` controla el buscador especializado bajo las mismas condiciones de servidor/modo y opt-in. Las solicitudes necesitan una API válida aunque el flag vehicular pueda evaluarse como verdadero sin URL.

`VITE_ALLOW_PRODUCTION_API=true` solo surte efecto en `serve` con modo `development` y desactiva ambos flags. `VITE_API_URL` determina la base API y `VITE_SERVICE_TIMEZONE` la zona horaria operativa, con valor predeterminado `America/Mexico_City`. La validación de URL y origen está en `src/config/apiEnvironment.js:7–46`. Reiniciar Vite tras cambiar variables locales.

Un `vite build` mantiene ambos flags en falso incluso con modo staging y valores `true`. Un cambio de variables del VPS después de compilar tampoco modifica el frontend. Para un piloto futuro con artefacto desplegable se requiere una modificación frontend autorizada y revisada que separe los controles de compilación actuales del alcance autenticado de cada piloto.

## Verificación del encabezado

La prueba del checkout exige que `POST /v2/sales` reciba el UUID en `headers["Idempotency-Key"]` y que una respuesta perdida se resuelva con un solo POST y el GET de la misma clave. El interceptor real de `axiosClientPOS` conserva ese header y añade `Authorization: Bearer <POS_TOKEN>`. Se comprobó con ambos tokens ficticios presentes y un adaptador en memoria, sin transporte. Véanse `src/hooks/POS/usePOSLogic.test.jsx:168–201` y `src/config/axiosClientPOS.js:4–18`. Las once ventas reportadas con ambos campos NULL son compatibles con el flujo tradicional sin encabezado y por sí solas no demuestran ni descartan que otros clientes usen idempotencia.

## Procedimiento de certificación

1. Preparar Laravel y MySQL aislados en una base desechable con el mismo esquema y versión previstos para el piloto. Verificar estado de migraciones, columnas e índice único de V2 y usar datos ficticios. Registrar una tienda, una sucursal, una terminal piloto, otra de control y una identidad de otra tienda. Establecer línea base de caja, inventario, ventas y permisos.
2. En una configuración local aislada usar `VITE_API_URL=<API de pruebas>`, `VITE_ALLOW_PRODUCTION_API=false`, `VITE_POS_SERVICES=true`, `VITE_POS_VEHICLE=false` y la zona horaria de prueba. Ejecutar Vite en modo desarrollo. Verificar en el navegador el origen y, si es un origen distinto, que CORS permita `Authorization`, `Content-Type` e `Idempotency-Key`. Entrar con código/PIN de una terminal ficticia.
3. Verificar el POS tradicional en la terminal de control. En la piloto habilitar `service_sales` a nivel tienda y luego con override explícito de terminal. Confirmar que `operational_enabled` solo sea true en la piloto. Probar acceso directo y errores con la terminal de control y la otra tienda. Habilitar `vehicle_records` y `service_forms` por separado y comprobar sus dependencias. Repetir después con `VITE_POS_VEHICLE=true` en la instancia de desarrollo para revisar búsqueda, detalle por ID, variantes y almacenes autorizados.
4. Recorrer agenda, disponibilidad, creación/reprogramación, recepción, orden, inspección, comprobante y vinculación con fixtures. Validar inventario por almacén, crédito y ventas pendientes. En una venta de prueba aislada, forzar pérdida de respuesta después del commit y recuperar con el mismo UUID. Comparar ID de venta e inventario antes y después. Probar conflicto de contenido 409 y concurrencia con misma clave en MySQL, confirmando una sola venta, un solo movimiento por partida y ausencia de duplicados en pagos o vinculación.
5. Desactivar la terminal piloto y verificar que su sesión deja de funcionar, el login nuevo falla y la terminal de control sigue operativa. Reactivarla y exigir nuevo login. Confirmar que un POS recibe 403 en reportes financieros y que el Store propietario puede consultar los suyos.
6. Aprobar el piloto solamente con evidencias HTTP depuradas, verificación de concurrencia, política de precios/descuentos resuelta y aprobación explícita de un cambio frontend que permita un piloto desplegable. Para idempotencia, el nuevo control debe seleccionar terminales autorizadas desde un contexto autenticado, dado que el flag actual abarca todas las terminales que usan esa instancia de desarrollo. Expandir a más terminales o sucursales solamente después de comprobar los mismos criterios en el piloto.

## Reversión

- Detener los nuevos cobros del piloto y reconciliar toda clave incierta o vínculo pendiente antes de retirar el frontend que permite recuperarlos. Conservar la API de recuperación, las claves y los registros de ventas durante el proceso. Si hace falta cortar la operación de inmediato, desactivar la terminal y conservar otra vía autorizada para la reconciliación posterior.
- Restaurar los valores de módulos registrados antes del piloto. Para una terminal que heredaba visibilidad de Tours, restaurar la herencia de `service_sales` con `enabled:null` y verificar `operational_enabled=false` mientras el acceso heredado esperado sigue visible. Un override explícito false puede ocultar también el módulo heredado.
- Tras reconciliar, volver al artefacto frontend aprobado anterior o desactivar la habilitación del piloto. Conservar migraciones, claves y hashes de las ventas registradas. Una terminal reactivada requiere sesión nueva.
